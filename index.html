How it works

One score. Four responses. No guesswork.

Every change-stream event feeds a damage-weighted score. The score — not a single rule — decides what happens next.

0.35Destructive-command ratedrop, dropDatabase and deleteMany commands per window
0.25Collection churnhow many collections are being hit, and how fast
0.25Data volume at riskvalue-weighted documents — orders count more than inventory
0.15Command rarityrare commands (drop, dropDatabase) score higher than routine writes
0 – 30

Watch

Score is tracked. Nothing is blocked. Normal traffic — bulk inserts, index builds, backups — stays under 30.

≥ 30

Throttle + snapshot

Attacker sessions are throttled (killSessions) and a snapshot is taken on suspicion, so there is something to restore from.

≥ 60

Suspend + quarantine

Writes are suspended and the attacker's role is revoked on the authenticated server — later batches fail with code 13.

≥ 85

Isolate + restore

The database is write-locked (fsyncLock) and the snapshot is restored — staging copy first, rename-swap only on success, verified against recorded counts.

What the lab proved about killing attacks: a drop() is not killable — killOp acknowledged, the drop still completed. killSessions interrupts one operation, not the session. So AurevoDB does not promise to kill a drop. It promises to detect it fast, limit what follows, and restore what was lost. That is the whole design.

Honest limits

What it does not do.

A product page that hides its limits is a brochure. These are measured, and they stay in the report.

  • dropdb prevention is 0% by design. A dropDatabase cannot be killed. The answer is verified fast restore (median 1,766.0 ms) plus least-privilege roles, not prevention.
  • Steady overhead is +242.8% mongod CPU. The ≤+43% target was proven unreachable: priming off still costs +49.1%, and only the 0.02 s priming rate keeps fast-delete alive. Not re-measured in v7; the v4 numbers stand.
  • Undeclared maintenance still looks like an attack — the v7 gate only halves it. The (b2) false-positive gate blocks escalations until ≥2 destructive bursts or one burst ≥1,000 value-weighted docs, and it halves FP escalations 6/18 → 3/18: a bulk-delete purge now escalates 0/3 times (the gate blocks it), but an orders drop-and-recreate still escalates 3/3 — one drop of 4,000 documents is a single burst of 4,000 value-weighted docs, above the threshold. The score itself still trips 3/3 on both workloads; the gate blocks actions, not the alarm. Declared maintenance is exempt and scores 0/18 false positives — undeclared work is not.
  • Fast delete is the least stable number: v7 median 29.54%, v6 was 54.08% — and the v8 probe says the hold is not the cause. At matched seeds, hold 3.0 vs 1.0 moves fast delete by −4.83 median points (paired, p=0.766) — noise. The lock never touches this attack at all: 0/135 batches start while locked, because the two deleteManys finish in ~0.5 s while the first lock verifies ~1.8–2.0 s after attack start. Saved % is set entirely by the first throttle kill interrupting the payments deleteMany. Any fix must move the first kill, not the lock — and no config change shipped (hold stays 3.0; reverting would cost interleaved ~22 points for a gain that is not established).
  • Finding 14 — the FP gate can block a real attack (small). In the v8 probe, slow at hold 3.0 had its N-escalation write-lock blocked by the gate in 2/27 runs (0/27 at hold 1.0). Saved % was unaffected — 68.00% either way, because the revoke, not the lock, saves slow.
  • Damage-prevented % is an upper bound. The emulator is not validated against real ransomware traces, and the lab baselines flatter the system. The report states this in full.
  • Interleaved is no longer the weakest shape. 57.64% median in v7 (v6: 32.60%) — the 3.0 s write-lock hold is the mechanism, dose-dependent: batches started while locked rise 45 → 66 → 89 across holds 1.0 / 2.0 / 3.0 in the v8 probe.
  • Late write-locks delayed two post-run probe writes in v7 (2/426 runs). A lock decision made just before watch-stop executed 1.6 s and 3.4 s late. The server was never left locked — every lock has a matching verified unlock. A measurement race, not a defence failure.
